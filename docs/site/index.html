phygen — system documentation

phygen evolves a generative artwork. A language-model session edits a small JavaScript package that renders a physarum transport network. Every accepted edit becomes a version. Versions keep their source, their configuration, their rendered frame, their cost, and the agent feed that made them. The result is a recorded history of an artwork, not a memory of one.

This document does four jobs. It explains the idea. It compares the four local git branches and the approach of each one. It describes the current architecture in detail. It collects the screenshots and the artwork captures.

Read this first. The repository has four branches. They are a single line of history: master → simple → slotmachine → behavior. The current branch is behavior. The screenshots in docs/ and the screencasts were recorded on the older tree interface, so they show master's user interface. The section The interface tells the two interfaces apart.

1 · Overview

One run makes a forward chain of versions. Each step authors exactly one child of the newest good version. The server renders the child, records it, and keeps it. A person judges the frames. There is no judge model on the current branch.

The four branches in one line each:

3.2 · The two approaches

The design question of the whole project is how a new version is chosen. There are two answers in the history. The first is the judged tree: make several variants, let a vision model judge them, and keep the tree. The second is the forward chain: make one child, keep it, and let a person judge the frames. The project moved from the first to the second and did not go back.

3.3 · Per-branch detail

master the judged tree

Thesis. A clickable artwork tree. You select a version, give a direction, and spawn a small brood of variants. A blind vision judge picks the winner. The tree keeps every sibling.

Evolution model. Three variants per evolution by default, clamped to 1–8. Each variant gets a fixed slot — refinement, structure, or experiment. A structural redirect fires after two unchanged levels. The judge is a separate model with its own picker. Judging is blind: anonymous labels, a randomised order, images only, and a strict JSON verdict. It runs in two phases — a round comparison of all variants with the parent as a reference, then a finalist against the parent with the order reversed and a tie-break.

Parent. The winning variant, or any node you click: a run can branch from a selected version.

Data model. Adds versions.round, versions.slot, versions.direction, versions.on_lineage, runs.direction, runs.unchanged_rounds, rounds.candidate_ids_json, jobs.slot, and the comparisons, evaluations, analysis_runs, and pair_measurements tables.

Interface. React Flow draws a radial tree: generation rings of cards around the root. Side panels show the detail, the relationships (config distance and source similarity), the captures, and a mobile generation list. A ?doc=1 recorder records the interface for the documentation.

Prompt. The author gets a direction, a slot assignment, an anti-repetition history, and the parent configuration as JSON.

Key commits: “Add the phygen evolution system”; “Lay the tree out under each parent, and branch from the selected version”; “Draw each parent's children as a ring, and make the interface answer a click”; “Call children variants and levels evolutions, and drop the cost guardrails”; “Write down how the system works, and what it measured”.

simple novelty and archive

Thesis. Make the judged tree run itself. Promotion needs novelty as well as quality, and the run picks its own parent from a small archive and writes its own direction.

Evolution model. Still a tree with variant broods, and still a judge. Two changes matter. First, a promotion must pass a novelty floor and a quality floor, so a near duplicate is refused. Second, the run chooses its own parent from an archive of up to eight members, either the furthest member or the best by quality. A comparison that never answers no longer stalls the run.

Parent. The run's own archive choice. The direction is written by the run.

Data model. The archive survives as a JSON artifact with fields quality, votes, wins, losses, confidence, novelty, and addedBy. The judge vocabulary and the floors live beside it.

Interface. The same React Flow rings, plus an appearance panel driven by a bounded vision call, follow-without-zoom, and a brood block beside its one branching child.

Prompt. The direction is authored by the run rather than typed by a person.

Key commits: “Promote on novelty as well as quality, and survive a comparison that never answered”; “Let a run choose its own parent from an archive, and write its own direction”; “Measure how different two versions LOOK, with a bounded vision call”; “Make the judge pick a variant…”; “Follow the work without moving the zoom, and record the tree”.

The lesson. The work of this branch did not survive in code. Its lesson did: novelty floors and parallel broods doubled the cost for winners that a person often did not prefer. That drove the next branch to the single-child chain.

slotmachine the forward chain

Thesis. Kill the slot machine. One button starts X steps. Each step makes exactly one child of the newest good version, and the child is always kept. No judge, no variants, no archive: the artwork grows as a forward chain, and the interface becomes a column of cards.

Evolution model. One child per step from the chain head. A child that passes the package checks is kept, whatever it looks like. There is no quality gate. The records still hold a round per step, with one candidate and whether it was promoted.

Data model. Removes comparisons, evaluations, analysis_runs, pair_measurements, versions.slot, versions.direction, jobs.slot, and runs.direction and runs.unchanged_rounds. Renames the run count from evolutions to steps in the interface. Renames the records directory from data/ to data-evolve/.

Interface. A vertical chain of large cards, newest at the top. Exactly one card plays live: the newest promoted version. A working step shows a deterministic pixel field. The card under the reading line plays, and the one before it stops.

Prompt. The slot templates are deleted. One fixed step instruction remains, and the calm-in-time render rules enter the pipeline.

Key commits: “Run the chain forward: one child per step, and no judge”; “Rebuild the interface as a chain of cards, and give a working step a pixel field”; “Play the card the view is on, and stop the one before it”; “Start the next artwork while the one above it is still a fifth visible”; “Keep the frame calm in time, and add the operator edit modes for the chain”.

behavior the operator

Thesis. Keep the forward chain, and make quality an operator affair plus a much stricter art brief: repair and fix tools, chain reset and truncation, authored prompts, and the chain committed to git as text.

Evolution model. Identical to slotmachine: one child per step, chain head, always kept, no judge, no archive. A technical failure gets one bounded repair session. A capture timeout is infrastructure and spends no repair. New operator paths appear: repair a failed version from its own snapshot back to promoted, fix a kept version in place with a checksum refusal for behaviour changes, refactor kept code, and reset or truncate the chain.

Data model. The schema is unchanged from slotmachine. The chain is mirrored as text in docs/chain.json by the chain-index tool, so the artwork history is committed with the code.

Interface. The card chain of slotmachine, unchanged. The pixel field, the reading line, the shell, and the modal all persist.

Prompt. A stricter STEP_INSTRUCTION: a substantial visual change that keeps the physarum identity, a hierarchy with quiet areas, no rainbow, and a pixel budget tied to the trail. The system prompt asks for one strong artistic decision per step, no flicker, integral alpha-over blending only, and a 30 fps target.

Key commits: “Let an operator fix kept versions in place, and add the chain frame, reset, and truncation tools”; “Add the operator modes for sharp pixels, a warm window, and colored-noise color”; “Ask each step for a substantial visual change, and keep the trail in charge”; “Keep the evolved artworks in version control, with the chain record as text”.

3.5 · What each branch contributed

  • master wrote everything that remains: the package contract, immutable snapshots, the sandboxed capture, budget accounting, the event stream, the agent feed, the preset and recorder tooling.
  • simple left no code in the line, but changed the direction of the project. It showed that broods and novelty floors cost more and did not buy better winners.
  • slotmachine is the hinge. It set the one-child step, the no-judge rule, the card chain, the pixel loading art, the autoplay reading line, and the calm-in-time rules. The core of the current system is its work.
  • behavior is additive. It keeps the chain and adds operator control, chain tools, the stricter art brief, and the chain record in version control.

4 · Current architecture (branch behavior)

The current system keeps the forward chain and adds operator control. This section follows one step through the controller, then describes the records, the events, the snapshots, and the recovery paths. The references use file:line so you can jump from the document to the source.

4.1 · The life of one step

A step is bounded. It authors one child, checks it, publishes it, renders it, and promotes it. A failure ends the step without moving the chain head. The order is fixed.

#StageWhat happensSource
1AdmissionPOST /api/runs validates the request and asks the budget whether the highest possible cost fits. A refusal happens before any record exists.app.mjs, budget.mjs
2Chain headRead the newest version with status promoted. On the first step that is the imported root.run.mjs:471
3AuthorCopy the parent snapshot into work…/<runId>/<versionId>. One session edits it with the fixed instruction, the manifest rules, the parent configuration, the run history, and the last three frames, newest first.run.mjs:1123
4ValidateCheck the edit surface, the package, and the configuration against the schema. A technical fault gets exactly one bounded repair session.run.mjs:1297
5PublishCopy the accepted workspace into snapshots/<artwork>/<hash>, atomically. The snapshot is immutable.workspace.mjs:192
6CaptureRender the child from the published snapshot: one 1024×1024 square, seed 1337, step 2500, dpr 1. Frames that match an existing hash are reused.run.mjs:1389, browser.mjs
7PromoteSet the status to promoted and mark the version on the lineage. It becomes the chain head for the next step.run.mjs:1661
The failure rule. A failed version does not become a parent. The next step starts from the last good version. A round with promoted: false and one failed candidate means the step failed a technical check. The chain keeps the work that was kept, and the interface hides the failed steps.

4.2 · The prompts

The author session receives one fixed instruction and one system prompt, plus the manifest rules, the parent configuration, the run history, and the frames. The instruction is the art brief. On this branch it is deliberately strict, because there is no judge to correct a weak step.

The step instruction

STEP_INSTRUCTION (prompts.mjs:9) asks for a substantial visual evolution, not another small variation. It keeps the core physarum algorithm: agents sense the shared trail, steer, move, and deposit into it. Trail feedback must stay the main cause of the visible forms. The instruction asks for one clear direction, a hierarchy with contrasting scales and quiet areas, and negative space. It names what does not count: a new color, a small parameter adjustment, an extra layer of noise, or full-spectrum rainbow color. A few lines carry the intent:

Create a substantial visual evolution of this artwork, not another small variation. Make fewer elements do more. Remove, reduce, or replace inherited effects that compete with the chosen direction. Give the image a clear visual hierarchy, contrasting scales, and quiet areas with little detail. Avoid uniform detail, dense coverage everywhere, competing centers, and full-spectrum rainbow color. Dynamic means clear development over time, not more effects, faster noise, or flicker. Keep the result reproducible, runnable, and visually clear at 1000 simulation steps.

The system prompt

EVOLVE_SYSTEM_PROMPT (prompts.mjs:44) is the artist-engineer charter. It fixes the identity: keep the core physarum algorithm and its trail feedback; change the visual expression, not the identity. It sets hard rules for a free picture. Do not force agents along a prescribed centerline and call the form emergent. Make one strong artistic decision per step. Implement it in source code; a numeric tweak alone is not enough. Change only allowed files and never a protected one. Add no dependency and run no shell command. Write no new comments. Keep a 30 fps target. Nothing may flicker on and off from one frame to the next: use normal alpha-over blending only, never additive, multiply, overlay, or screen. Report the intent, the main change, and the competing effects that were removed.

The assembled prompt

buildEvolvePrompt (prompts.mjs:81) assembles the instruction, the manifest rules, a short map of the artwork source, a direction-planning block, an accumulated-image block, seven numbered requirements, the history of this run, the parent configuration as JSON, a frame hint, and an end-of-review checklist. The frame hint is exact about what an image proves:

The attached frames are ordered newest first. The first frame is the parent; later frames show earlier versions. Use these images to assess composition and visual repetition. A still frame does not prove motion quality or frame rate.

Repair and refactor

buildRepairPrompt (prompts.mjs:203) is one bounded attempt. It gives the failure code and text and asks the session to repair the workspace in place and keep the same artistic intent. REFACTOR_SYSTEM_PROMPT and buildRefactorPrompt (prompts.mjs:161) are a different job: change the shape of the code, never its behaviour. The same seed and step count must give the same image. The refactor removes every comment, does not touch config.json, and does not rename a public method or a file.

4.3 · Origins and the capture

The controller and the artwork run on two origins. This is a security boundary, not a preference. Generated and imported code is untrusted, so it never shares an origin with the API or the credentials.

The capture (capture/browser.mjs) opens one fresh browser context per call and one fresh page per sample. The page URL is fixed by query parameters: ?steps=2500&seed=1337&speed=8&paused=0&dpr=1. The page signals window.__ready, __done, or __failed. The capture rejects window.__error, screenshots the viewport, and reads the trail checksum, the agent checksum, the fps, and the renderer backend back out of the page. A Node-side deadline races the whole batch and tears the context down on expiry: at least 30 s per sample plus a 30 s margin.

The container path (capture/docker.mjs) is the stronger boundary: no network, a non-root user, read-only filesystem and image mounts, CPU, memory, pids, and time limits, with job.json in and result.json out. PHYGEN_CAPTURE selects auto, local, or docker. Without a container, set PHYGEN_REQUIRE_ISOLATION=1 and the controller refuses source-code children.

4.4 · Version statuses and the playing rule

A version moves through a small set of statuses. Exactly one version plays live: the newest one with status promoted. Every other version shows its still frame, its stage, or its failure reason. A failed step is not drawn in the chain.

The interface rule is pure and tested without a browser (web/src/chain.ts):

  • chainOrder sorts newest first by generation, then by creation time.
  • playingVersionId returns the newest promoted version. Every other version shows a still.
  • READING_LINE_FRACTION is 0.2. The reading line sits at a fifth of the distance between two cards, so the artwork above is down to about a fifth of its height when the next one starts to play.
  • visibleCardId returns the lowest card whose top edge is still above the reading line. Scrolling down stops one artwork and starts the next.
  • autoplayCardId handles the working case: a card still being made has no snapshot, so the newest artwork that can play takes over while the step in progress shows its pixel field.
  • stepLabels names the root Root and every other version Step N. Two attempts can share a generation, because a failed step starts again from the same parent; a second attempt gets a letter, so two cards never carry the same name.

4.6 · The event stream

The controller writes an event once and every client replays exactly what it missed. EventBus.emit appends the event to the store first, then fans it out to the open subscribers of that run. The stream route subscribes before it replays, pages the complete missed range 500 events at a time, and flushes the buffered live events in order. A client that falls too far behind is closed rather than trimmed, so no gap is hidden: it reconnects with its last sequence number and receives the range it missed.

4.7 · Snapshots

A published snapshot is immutable. The server writes it by a small protocol so that two writers can never corrupt one hash.

  1. Hash the package-relative paths and copy into a unique .pending-… directory. Recompute the hash and check it against the validated hash.
  2. Write snapshot.json exclusively. Never overwrite an existing marker.
  3. Rename the pending directory into place. A rename is atomic. If a concurrent winner exists, re-verify it and remove the losing directory.
  4. Reuse an existing directory only when verifySnapshot proves that its contents hash matches.

4.8 · Control and recovery

  • Pause stops new steps after the current bounded step. The interrupted step is recorded and does not consume a step. Resume continues it and reuses the child the run already published.
  • Stop ends the run. Work already published stays. A stop is checked before every reservation, every retry delay, and every provider start, so a stopped run can never start another paid session.
  • A configured limit stops the run and names the limit. It does not consume a step and does not look like a candidate fault. By default no cost limit is enforced: the record keeps the real spend.
  • A restart pauses unfinished runs for review. Nothing is resumed automatically. A restart revives a published snapshot that was in flight.
  • The event stream subscribes before it replays, pages the complete missed range, and closes a client that falls too far behind, so no event is lost and no gap is hidden.
  • The operator can repair a failed version from its own snapshot, fix a kept version in place, refactor it, reset the chain to the root, or truncate it at a generation.

Cost

Before each provider call the server reserves the highest cost of that call. After the call it commits the real cost, or the bound when the provider reports none. The reserve, the commit, the cost source, and the token count are all recorded per call. The estimate before a run uses catalog prices and an expected token count; the record keeps the real cost. A cost limit is enforced only when you set one.

5 · The interface

Which interface is in the pictures. The screenshots in docs/ and the screencasts were recorded on the master branch, before the chain rewrite. They show the tree interface: generation rings, variant broods, and the judge. The current behavior interface is different. Read this section for the current interface, and read the galleries as a record of the tree era.

5.1 · The current interface (behavior and slotmachine)

  • The header holds the model list, the step count, and one button: Evolve.
  • The chain is one vertical column of large cards, newest at the top. A card holds the step number and title, a 1024×1024 square, the changed files, the tokens, and the cost.
  • Exactly one card plays live: the newest promoted version. Every other card shows its still frame or its stage. A failed step is not shown at all.
  • A card that is still being made has no snapshot yet, so it shows a deterministic pixel field instead. The field is a 200×200 vector grid of 4 px cells: each particle is exactly one cell, moves whole cells, and turns at most a quarter turn on arrival. The rule is in web/src/texture.ts.
  • The shell is a read-only log of the agent, newest at the bottom. It follows the work while a step runs and shows the stored log of a selected card. A tool row names the tool, the short path, and the line counts. The reasoning rows are dim.
  • The chain and the shell are separated by a drag handle. The split starts at half the height and is kept in localStorage.
  • The status line shows the state, step X of Y, the spend, the provider, and whether the stream is live.

5.2 · The tree interface (master and simple) — what the pictures show

  • The header holds the direction text, the evolution count, the variant count per evolution, the judge model, the author model, and an optional cost limit.
  • The canvas is a radial tree: each parent's children are drawn as a ring around it. The root sits at the top left, its three variants below, and their winners below them.
  • Each card shows a frame, the slot name (refinement, structure, experiment), the generation, and the status. A winner carries a WINNER! badge; a rejected sibling carries a YEETED! badge.
  • The right panel shows the selected version: generation, status, source hash, the author explanation, the source changes, the configuration, and the visual evidence (the capture stages).
  • The status bar shows the provider, the capture mode, the stream sequence, the run state, the spend, the call counts, and the per-kind job counts.
  • A ?doc=1 documentation recorder records the canvas for the screencasts. The recorder counter is visible in the status bar of the recording frames.
  • Mobile shows a generation list instead of the canvas.

GET /api/runs/:runIdOne run with its jobs and usage.
GET /api/runs/:runId/summaryA small payload the interface polls while a run moves.
POST /api/runs/:runId/pauseNew steps stop; the current bounded step finishes.
POST /api/runs/:runId/resumeContinue a paused run.
POST /api/runs/:runId/stopEnd the run. Active tasks are cancelled where the driver supports it.
GET /api/runs/:runId/eventsServer-sent events. Send Last-Event-ID to replay from a sequence number.

Every other path returns the built interface (web/dist/index.html). When the interface is not built, the server returns a page that says so.

11 · Operator tools

The interface has no button for these. They exist for an operator. Every tool is under server/tools/ and runs from server/.

ToolPurpose
repair-version.mjsOperate on one version: repair, capture-only, refactor, revive, and the in-place display fixes (fix-blend, fix-aa, kill-strobe, remove-settle, soften-clear, calm-forces).
capture-frame.mjsCapture frames for a version outside any run. --force drops old frames. The server must be stopped.
reset-to-root.mjsDelete all evolved versions, runs, workspaces, and unreferenced snapshots; keep the root mother.
truncate-chain.mjsKeep versions through a generation and remove the rest. Refuses on active runs.
chain-index.mjsExport the chain (parent lineage, status, config, hashes) as JSON for version control.
snapshot-report.mjsRead-only integrity verification of every snapshot directory.
backup.mjsOne consistent copy of the records and their files, by SQLite VACUUM INTO.
live-check.mjsVerify that an artwork plays both directly and through the sandboxed embed.
failed-steps.mjsRead-only post-mortem of failed versions, with reasons, jobs, and events.
clear-stale-jobs.mjsClose jobs and versions left in flight by a killed tool. Never touches active runs.

The test double

PHYGEN_DRIVER=fake runs a deterministic stub instead of a model. Its code changes are canned, and every card it produced carries a test double chip. Work made by the stub is not work.
